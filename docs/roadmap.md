# Что ещё нужно для полноценной классификации

Текущая система является работающим MVP: есть FastAPI, web-страница загрузки
PDF, Docker-запуск, OCR через мультимодальную LLM, retrieval и evaluation на
небольшом реальном наборе. До production-классификатора всё ещё не хватает
масштабной оценки качества, наблюдаемости, политики неопределённости и
эксплуатационных гарантий.

## P0 — качество и корректность

1. **Подтверждение справочника subtype.** Справочник перенесён в JSON; требуется
   официально подтвердить написание кода `П.3.4`.
2. **Расширение evaluation-выборки.** Текущий `real_v3.json` содержит 16
   размеченных документов. Нужно собрать 300–500 обезличенных обращений с
   эталонными themes, questionType и questionSubtype, включая мультитемные,
   короткие, шумные и пограничные случаи.
3. **Quality gate.** Сейчас метрики считаются для top-1/3/10/20/30/50 retrieval,
   themes, type и subtype. Нужно закрепить минимальные пороги качества, fallback
   rate и долю ручной эскалации.
4. **Subtype.** После anchor-based retrieval и typeDecisionText главная слабая
   зона — subtype. Нужны дополнительные правила/примеры и экспертная проверка
   границ `2.1.1`, `2.2.1`, `2.2.2`, `2.2.3`, `3.1.1`, `3.2.x`.
5. **Политика неопределённости.** Сейчас fallback всегда стремится выдать тему.
   Нужны пороги confidence, статус `needsReview` или эквивалент и запрет на
   автоматическое решение при недостаточной уверенности.
6. **Проверка качества исходного справочника.** Эксперт должен разобрать 5
   дублей, 11 невалидных/footnote-кодов и правила использования 766
   пятиблочных кодов.

## P1 — надёжный сервис

1. **API-контракт.** Базовый FastAPI-контракт уже есть. Нужно стабилизировать
   версионирование ответа, лимиты, timeout и контракт PDF-артефактов.
2. **Наблюдаемость.** Добавить структурные логи без персональных данных, latency и error
   metrics по шагам, token/cost accounting, fallback rate и trace request ID.
3. **Устойчивость LLM.** Таймауты, ограниченные retry с backoff, circuit breaker,
   контролируемая concurrency и явное различение provider error и model error.
4. **Безопасность секретов и ПДн.** Убрать действующие ключи из исходников и
   истории Git, использовать secret storage, определить правила маскирования,
   хранения и передачи обращений внешнему LLM-провайдеру.
5. **Конфигурация.** Вынести модели, веса, top-K, пороги и версии артефактов в
   валидируемые settings; зафиксировать зависимости lock-файлом.
6. **Атомарные версии артефактов.** Хранить manifest/checksum для JSON, BM25,
   embeddings и FAISS и переключать их только единым релизом.

## P2 — промышленная эксплуатация

1. **Интеграционные и end-to-end тесты.** Отдельный opt-in набор с реальным
   embedding/LLM provider, проверкой CLI/API и бюджетными лимитами.
2. **CI/CD.** Unit-тесты, lint/type checking, dependency/security scan,
   сборка образа и quality regression перед релизом.
3. **Контейнеризация и health checks.** Docker Compose уже есть. Нужно добавить
   production-проверки окружения, smoke-запуск PDF-классификации и ограничения
   concurrency.
4. **Кэширование.** Кэш embeddings запросов и, при допустимости, результатов
   повторных обращений для снижения latency и стоимости.
5. **Human-in-the-loop.** Интерфейс проверки низкоуверенных результатов и
   накопление исправлений для следующего evaluation/обучающего набора.
6. **Мониторинг дрейфа.** Следить за изменением распределения тематик,
   неизвестными формулировками и падением качества после обновления
   классификатора или LLM.

## Рекомендуемый ближайший milestone

Сначала не добавлять новые сложные компоненты. Зафиксировать 300–500
обезличенных размеченных обращений, получить baseline-метрики текущего
anchor/typeDecisionText pipeline, закрыть официальный subtype-справочник и
определить пороги ручной проверки. После этого решения по subtype, threshold,
стоимости и API будут опираться на измерения, а не на отдельные удачные
примеры.
